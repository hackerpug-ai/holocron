# Technical Risks

Ordered by impact then likelihood. Every entry names a mitigation; the ones marked **blocking**
must be resolved before the sprint that depends on them starts.

## Blocking prerequisites — ahead of every feature sprint

### 1. `npx vinext check` has not been run

vinext is beta. It must confirm: unbuffered streamed responses; Route Handlers returning a streamed
binary body; `cloudflare:workers` bindings inside Server Components and Route Handlers; `proxy.ts`
support and whether `caches.default` is reachable from it; `next.config` `headers()` honouring the
non-standard `Cloudflare-CDN-Cache-Control` key; `not-found.tsx` returning a true 404 status;
`generateMetadata` on a dynamic segment; Tailwind v4 + React 19. Discovering any of the first six is
unsupported *after* the app is built is the single most expensive failure available in this plan.

### 2. The web surface has NO e2e framework

Reality Gate, deterministic: no `@playwright/test`, cypress or puppeteer anywhere in dependencies;
`.e2e/` contains only `maestro/`. This becomes a leading INFRA sprint that every feature sprint
depends on, and it should not be scored against product acceptance criteria.

### 3. The seeder cannot test the defect this PRD exists to fix

Verified: `seed-e2e.ts:623` mints deterministic share tokens, but the seeder has **zero** references
to `document_assets`, `file_objects` or `BlobStore`, and **zero** image markdown. A web suite could
go fully green without ever rendering an image. Fix: attach a real `document_assets` + `file_objects`
row, a real blob, and both a document-relative and a remote image to an **existing** seeded
document — never an eighteenth, because `seed-e2e.test.ts` asserts `documents === 17` in the JSON
self-report and twice via live `psql`.

### 4. The origin returns HTML, not markdown

`hono-app.ts:148` calls `articleHtml(article)` unconditionally. Roughly five lines to content-
negotiate, but the public reader cannot start without it and no lens has claimed ownership.

### 5. The Workers plan is unconfirmed

Workers Free caps CPU at 10ms per request; an agent loop with MCP tool marshalling will not fit.
Awaiting `fetch` does not consume CPU, so Paid is expected to suffice — but the existing Worker's
comment implies a free *zone* plan, which is a different setting and does not answer this.

## Mitigations

### 1. The origin's GET /article/:shareToken returns rendered HTML, not markdown. The Next Server Component cannot render what it needs from that response, so the entire public reader is blocked on a small origin change that currently has no owner in this plan.

**Impact** high · **Likelihood** high · proposed by `nextjs-planner`

**Mitigation.** Scope it explicitly as a prerequisite in build-order step 1: content-negotiate on Accept: application/json in packages/platform/src/http/hono-app.ts around line 148 and return c.json(article). selectPublicArticle() already produces the exact ArticleDoc shape. Keep the HTML branch alive so packages/docs-reader retires after the Next route is verified against production data, not before.

### 2. BetterAuth's settled requirement ('tables in platform Postgres') has no existing TCP-capable path from the Worker to the device - only an HTTP-only Access app exists today. Hyperdrive can't be wired to nothing.

**Impact** high · **Likelihood** high · proposed by `cloudflare-workers-planner`

**Mitigation.** Cross-lens decision with BetterAuth planning: either open a new TCP tunnel surface to Postgres (Hyperdrive-compatible), or move session validation behind an HTTP endpoint on origin's Hono app. Do not let this get assumed away as 'just add Hyperdrive' - the tunnel doesn't exist yet.

### 3. The brief's premise that device-Postgres auth means 'no new infrastructure' does not hold. The Next app runs at the edge; the tunnel carries HTTP with CF Access service tokens, not the Postgres wire protocol. Reaching device Postgres from a Worker requires either Hyperdrive with a private-network tunnel route, or a hand-written BetterAuth HTTP adapter.

**Impact** high · **Likelihood** high · proposed by `betterauth-planner`

**Mitigation.** Put the four auth tables in D1 (recommendation, see open_questions). If one-database is preferred anyway, use Hyperdrive over the existing Tunnel with the CF Access service token pair already in the secret index - and verify Hyperdrive availability on the account's Workers plan before committing. Reject the hand-written HTTP adapter outright: auth internals are the worst place in the system to write bespoke code.

### 4. The asset subroute /d/[token]/assets/[id] is brand new - there is no incumbent implementation to copy - so it is the most likely place for the token validator, the cache headers, the no-cookie rule, and the guard exclusion each to be dropped independently.

**Impact** high · **Likelihood** high · proposed by `betterauth-planner`

**Mitigation.** Treat page route and asset route as one boundary with one shared helper (validate -> cache-key -> origin fetch with Access headers -> fresh Headers -> cache). Every public_boundary verification runs against both paths, not just the page.

### 5. Next's default Cache-Control for a dynamic page (private, no-cache, no-store, max-age=0, must-revalidate) conflicts with or overrides the required header pair, and the conflict is invisible: the page renders perfectly while the 60s SLA silently becomes a per-request origin hit or a 7200s zone-floor stale window.

**Impact** high · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** Assert both headers via next.config headers() on source '/d/:token', then prove with a real curl against a deployed Worker on both a 200 and a 404 - never infer from local dev. If the framework header cannot be overridden, fall back to serving /d/[token] from a Route Handler that owns the whole Response, trading generateMetadata ergonomics for header control.

### 6. Responses generated by a Worker are not automatically placed in Cloudflare's edge cache - explicit Cache API use is required - and it is unverified whether vinext exposes caches.default from proxy.ts. If it does not, nothing caches and every request wakes the device.

**Impact** high · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** Item 4 of the vinext check. Fallback: move /d/[token] and its asset route to Route Handlers that call caches.default.match/put directly, which is the same escape hatch as the previous risk and can be taken once for both.

### 7. httpBatchStreamLink requires genuinely unbuffered chunked responses through vinext beta. If responses are buffered, the chat surface silently degrades from streaming to a single late blob - technically working, experientially dead, and easy to miss in dev where latency is near zero.

**Impact** high · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** Item 1 of the vinext check, verified against a deployed Worker with an artificially slow generator so buffering is visible. This gates the entire Chats surface (build-order step 4), not the public reader (step 1), so the two can be sequenced independently.

### 8. Response streaming may be buffered somewhere in the Next-on-Workers path (vinext is beta), turning httpBatchStreamLink into a single flush at turn end. Every persona promise about watching work happen dies silently - the turn still 'works', just all at once after 40 seconds.

**Impact** high · **Likelihood** medium · proposed by `trpc-planner`

**Mitigation.** Build order step zero for this lens: a throwaway debug.ticker async-generator procedure yielding 3 chunks 1s apart, deployed to a real Worker, asserting >=2 distinct client-side arrival timestamps. Do this BEFORE the router, the agent loop, or the reducer. If it fails, the whole streaming design is invalid and must be escalated, not worked around.

### 9. The device's search/list tool schemas cannot express filters or return the fields a Library row needs. This is a cross-repo dependency on the device team; if it slips, the Library ships without filter chips or share badges - which removes the audit journey and one of the operator's top-three needs.

**Impact** high · **Likelihood** medium · proposed by `trpc-planner`

**Mitigation.** FR-BFF-11 is a sprint-blocking prerequisite, sequenced before the Library task. It is an EXTENSION of two existing Zod schemas (hybridSearchInputSchema, SearchResultItemSchema), not a new tool surface, so the diff is small and additive. Do not accept a Worker-side filtering workaround: it breaks cursor pagination and reads the whole table over the tunnel.

### 10. Agent-loop CPU on Workers. A multi-tool turn may exceed the plan's CPU budget mid-stream, dropping the connection with no resume path.

**Impact** high · **Likelihood** medium · proposed by `trpc-planner`

**Mitigation.** Confirm the account is on Workers Paid BEFORE building (the brief flags that the existing Worker's free-ZONE comment does not answer the Workers-PLAN question). Time awaiting fetch does not count as CPU, so a tunnel-bound turn should be dominated by wall time, not CPU - but the AI SDK's own parsing does count. Instrument CPU per turn in the CAP-BFF-01 proof and record the tool-count ceiling.

### 11. The MCP gateway's enableDnsRebindingProtection + allowedOrigins may reject the Worker-to-tunnel call in practice even though it theoretically should pass (no Origin header on server-to-server fetch) - this is explicitly UNPROVEN per the design brief.

**Impact** high · **Likelihood** medium · proposed by `aisdk-planner`

**Mitigation.** First implementation task must be a real end-to-end probe: a Worker (or wrangler dev locally) calling createMCPClient against the real tunnel URL and confirming tools/list succeeds, before any agent-loop code is built on top of it.

### 12. Root-level node_modules/ai in this repo resolves to a stale v6 (6.0.116) while packages/platform correctly has v7.0.28 via pnpm - if the new web client package isn't pinned and isolated correctly, tooling could silently pick up v6 APIs (system, fullStream, parameters) during implementation.

**Impact** high · **Likelihood** medium · proposed by `aisdk-planner`

**Mitigation.** Web client's package.json must declare ai@^7 explicitly; implementer should run `pnpm why ai` inside the web client package before writing any AI SDK code to confirm resolution.

### 13. vinext is beta and `npx vinext check` has not been evidenced as run against this app's actual shape (streaming tRPC, middleware, custom domain, server-only bindings).

**Impact** high · **Likelihood** medium · proposed by `cloudflare-workers-planner`

**Mitigation.** Run the check as literally the first build step, before any other edge work is scoped or estimated. Treat a failing/partial result as a blocking architecture decision, not a task to work around.

### 14. Workers plan (Free vs Paid) is unconfirmed for this account. Free's 10ms CPU/request will not reliably support an AI SDK agent loop with MCP tool marshalling.

**Impact** high · **Likelihood** medium · proposed by `cloudflare-workers-planner`

**Mitigation.** Confirm the account's Workers plan before any agent-loop work starts (FR-EDGE-05). This is explicitly flagged as open in the design brief and must not be assumed.

### 15. The negative-matcher bug: a guard written as /((?!api|_next|d).*) silently ungates every route beginning with d, or a variant gates /d/*.

**Impact** high · **Likelihood** medium · proposed by `betterauth-planner`

**Mitigation.** Positive allowlist matcher, enforced by a test that evaluates the real matcher regexes against a real /d/share-<uuid> path. Never a lookahead.

### 16. cloudflare:workers env leaks into a client bundle through an import chain nobody traced, putting a Cloudflare Access service token in browser-shipped JavaScript.

**Impact** high · **Likelihood** low · proposed by `nextjs-planner`

**Mitigation.** FR-NEXT-16: one module, server-only import at its top so the failure is a build error naming the file, plus a CI grep asserting the specifier appears exactly once.

### 17. The MCP transport's enableDnsRebindingProtection: true with allowedOrigins: [request.url origin] may reject Worker-to-device calls if the runtime attaches an Origin header.

**Impact** high · **Likelihood** low · proposed by `trpc-planner`

**Mitigation.** Prove with one real Worker-to-device MCP call before any code depends on it (the brief already flags this as a first-contact check). If it rejects, the fix is device-side config, not a BFF workaround.

### 18. MCP transport's allowedOrigins/DNS-rebinding-protection setting is unverified for server-to-server Worker-to-device calls; if it silently rejects requests, the entire agent tool surface breaks with no obvious cause.

**Impact** high · **Likelihood** low · proposed by `cloudflare-workers-planner`

**Mitigation.** Prove this with a real call against the real device gateway before any agent-loop implementation work is scheduled - this is explicitly called out as unverified in the design brief.

### 19. The CF Access service token leaks (into a Client Component, a log line, a vars entry, or an error page).

**Impact** high · **Likelihood** low · proposed by `betterauth-planner`

**Mitigation.** Wrangler secrets only. The existing 'Never log Access headers' rule carries into the Next code. Add the credential names to the verify:no-server-secrets-in-client gate. Note the compensating control that already exists: the origin enforces is_public independently, so a leaked token does not by itself unlock private documents through the public reader path - but it does unlock /api/*.

### 20. A scaffold or CLI run from the repo root or from packages/mobile writes Next/shadcn files over the Expo app's app/, components/, components.json, global.css or tailwind.config.js.

**Impact** medium · **Likelihood** high · proposed by `nextjs-planner`

**Mitigation.** FR-NEXT-01. Every shadcn and ai-elements CLI invocation is documented with cwd=packages/web and invoked through pnpm --filter @holocron/web so the cwd is structural rather than remembered. The monorepo migration already enrolls packages/web via the packages/* glob, so no pnpm-workspace.yaml edit precedes scaffolding; the first scaffold replaces the private @holocron/web placeholder in place.

### 21. Every turn opens a fresh MCP client (Workers are stateless), paying initialize + tools/list over the tunnel before the first token. On a sleeping or slow device this is dead time the operator reads as a hang.

**Impact** medium · **Likelihood** high · proposed by `trpc-planner`

**Mitigation.** Yield turn-start immediately, before the handshake, so the UI has something honest to show. Cache the tool-list result in Worker module scope (survives within an isolate) or KV with a short TTL, and revalidate lazily. Measure handshake latency in the CAP-BFF-01 proof and record it.

### 22. The BFF reuses the mobile app's HOLO_KEY_RN and the shared HOLO_KEY_MCP. Revoking web access revokes the phone; an abuse or leak cannot be attributed to a surface; /api/chat-runs scope-based ownership cannot distinguish them.

**Impact** medium · **Likelihood** high · proposed by `trpc-planner`

**Mitigation.** FR-BFF-13 - add a web scope. The middleware is already a scope table (isScopeAllowedForPath), so it is one enum member, one branch, one secret. Route it past security-reviewer since it touches the tunnel boundary.

### 23. @ai-sdk/mcp's documented lack of notification support means the gateway's forwarded MCP progress notifications will never reach the web agent, even though the design brief describes them as forwarded end-to-end.

**Impact** medium · **Likelihood** high · proposed by `aisdk-planner`

**Mitigation.** Do not build any UI affordance that assumes live progress ticks during a tool call in the web client. Long-running work must go through the device-job hand-off pattern (CAP-AGENT-02) rather than in-tool-call progress streaming.

### 24. The local LiteLLM fleet is unreachable from the Worker, forcing 100% of web-client model spend onto the Anthropic API with no local-fleet cost offset - a real budget item not previously priced in section 7's accepted costs.

**Impact** medium · **Likelihood** high · proposed by `aisdk-planner`

**Mitigation.** Track token spend per turn from day one (reuse the existing budget-ledger/telemetry pattern in packages/platform/src/inference/ conceptually, even though that code itself stays mobile-only); consider a future tunnel route exposing LiteLLM if cost becomes material - explicitly out of MVP.

### 25. If co-located in device Postgres: the new tables land outside the zero_pub publication and outside the holocron_app role grants.

**Impact** medium · **Likelihood** high · proposed by `betterauth-planner`

**Mitigation.** Two opposite requirements, both real. (a) zero_pub is an explicit CREATE PUBLICATION ... FOR TABLE list (migration 0002), so new tables are excluded by default - that is CORRECT and must stay that way; auth rows must never sync to the phone. (b) migration 0007 shows this database runs a least-privilege holocron_app role, so the auth tables need explicit GRANTs for whatever role BetterAuth connects as, or the first sign-in fails with permission denied at runtime rather than at migration time. Not applicable under the D1 recommendation.

### 26. Markdown parse cost for a 4,000-word document on every cache MISS consumes Worker CPU budget, compounding with whatever the agent loop needs.

**Impact** medium · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** The parse is pure-JS AST work with no I/O and happens at most once per 60s per PoP per document, so the ceiling is bounded. Measure real CPU time via wrangler tail on the largest document in the archive before assuming it fits; if it does not, that is an argument for precomputing rendered HTML on the device at publish time rather than for a different parser.

### 27. The sanitiser silently over-strips: a tightened schema drops width/height/title on img or an attribute a figure caption depends on, so images appear but render badly, reproducing the shape of the bug being fixed.

**Impact** medium · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** FR-NEXT-23's golden-file test over real published documents. A sanitiser schema is only trustworthy against the content it will actually see.

### 28. DocumentBody gets forked between the operator view and the public page under time pressure, and the operator's preview stops being a faithful preview - which is precisely how every shared document stayed silently text-only for a year without anyone noticing.

**Impact** medium · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** One module, one snapshot test diffing both call sites (FR-NEXT-07). The test failing is the only cheap way this gets caught.

### 29. Next 16 renamed middleware.ts to proxy.ts and proxy runs on the Node.js runtime with edge explicitly unsupported. Under vinext the host runtime is workerd, so the compatibility of that combination is unestablished.

**Impact** medium · **Likelihood** medium · proposed by `nextjs-planner`

**Mitigation.** Item 4 of the vinext check covers this directly. Because proxy.ts holds only cache mediation and no auth in this design, a negative result degrades caching rather than breaking correctness or leaking auth - and routes straight to the Route Handler fallback.

### 30. Invalidation storm: a six-tool turn emitting an invalidate per tool causes a burst of documents.byId refetches, each a tunnel round trip to a device that is already busy serving the same turn's tool calls.

**Impact** medium · **Likelihood** medium · proposed by `trpc-planner`

**Mitigation.** Coalesce invalidate parts in a 250ms window keyed by (kind, id) before touching the query client (FR-BFF-15). Prefer emitting invalidate at turn-finish for records the turn only read.

### 31. Device schema drift. BFF output schemas are hand-maintained allowlists over device tool outputs; a device-side field rename ships a runtime parse failure to the operator rather than a type error at build time.

**Impact** medium · **Likelihood** medium · proposed by `trpc-planner`

**Mitigation.** Derive BFF output schemas FROM the device's exported Zod schemas (packages/platform/src/tools/schemas/*.ts) where the shape is already precise (deepResearchResultOutputSchema, shareDocumentOutputSchema are exact and reusable). Hand-write only where the device returns an opaque record (get_document, list_documents), and add a contract test that calls the real device and parses with the BFF schema.

### 32. Losing the accepted-cost boundary: without turn-boundary persistence (FR-BFF-10) a reload discards the entire conversation, not just the in-flight turn - a much larger loss than the one recorded as accepted in the brief.

**Impact** medium · **Likelihood** medium · proposed by `trpc-planner`

**Mitigation.** FR-BFF-10 plus FR-BFF-12. Persist at turn-finish, batched. The UI should state plainly that an interrupted turn is lost, rather than silently showing a truncated thread.

### 33. Workers CPU/time limits could truncate a streamText turn mid-flight with no resume mechanism (accepted cost), and the reducer might misinterpret an abrupt stream close as a clean finish rather than a failure.

**Impact** medium · **Likelihood** medium · proposed by `aisdk-planner`

**Mitigation.** Reducer must treat a stream that ends without a finish part as an error state and surface it, not silently show a truncated-but-'complete'-looking message.

### 34. The asset proxy route, if implemented by mirroring the existing reader's arrayBuffer() pattern, fully buffers each asset into the 128MB isolate memory before responding - fine for small images, risky for larger PDFs/screenshots, and adds latency the streaming alternative wouldn't.

**Impact** medium · **Likelihood** medium · proposed by `cloudflare-workers-planner`

**Mitigation.** Stream the origin response body through directly (new Response(originRes.body, { headers })) rather than buffering, consistent with the Rosetta KB's r_stream_responses guidance - buffer only if the Cache API write requires a materialized body (verify this against vinext's actual Cache API surface).

### 35. scrypt password hashing exceeds the Workers CPU budget on sign-in.

**Impact** medium · **Likelihood** medium · proposed by `betterauth-planner`

**Mitigation.** Set compatibility_flags: ["nodejs_compat"] and measure a real sign-in's CPU time under a real deploy. Brief section 7 already suspects Workers Paid is required; this is one more input to that confirmation. If it bites, passkeys (ECDSA verify) are dramatically cheaper than scrypt and are the natural upgrade.

### 36. vinext is beta; middleware.ts may not behave as the Next docs describe.

**Impact** medium · **Likelihood** medium · proposed by `betterauth-planner`

**Mitigation.** The guard is deliberately not the security boundary, so a silent no-op costs UX, not data. Verify the redirect with a real cookie-free request against a real build as part of brief build-order step 2.

### 37. Table-name collision if BetterAuth tables are co-located in the device Postgres - user, session, account, verification are generic names in a schema that already carries ~90 tables (verified: no collision today, but user_preferences, rate_limits, and rate_limit_tracking are close neighbours).

**Impact** medium · **Likelihood** medium · proposed by `betterauth-planner`

**Mitigation.** If co-located, set modelName to auth_user / auth_session / auth_account / auth_verification and set BetterAuth's rateLimit modelName away from rate_limit. Not applicable under the D1 recommendation.

### 38. Share tokens indexed by search engines or leaked via Referer to sites the document links out to.

**Impact** medium · **Likelihood** medium · proposed by `betterauth-planner`

**Mitigation.** X-Robots-Tag: noindex and Referrer-Policy: no-referrer on public responses. Neither harms unfurls - preview bots read OG tags regardless of noindex, which is what the cold-stranger persona actually depends on.

### 39. Adopting Next 16 cacheComponents ('use cache' / cacheLife) on top of vinext beta stacks two immature systems, and cacheComponents removes the revalidate, dynamic and fetchCache segment configs an implementer may otherwise reach for.

**Impact** medium · **Likelihood** low · proposed by `nextjs-planner`

**Mitigation.** Do not enable cacheComponents for MVP. The public reader's cache lives at the Cloudflare edge by design (FR-NEXT-15), so the framework-level cache buys nothing here and costs a second beta.

### 40. tRPC v11 + the repo's pinned zod@4.4.3. If the pin and tRPC's schema handling disagree, the fix is either a zod bump (which touches the device tool registry - a much larger blast radius than the web client) or a tRPC downgrade (which loses streaming mutations).

**Impact** medium · **Likelihood** low · proposed by `trpc-planner`

**Mitigation.** Validate with ONE real procedure carrying a real zod@4.4.3 input schema on day one, alongside the debug.ticker probe. Both probes are the same afternoon and de-risk the entire lens.

### 41. Cloudflare Access service-token rotation isn't handled distinctly from any other origin failure - a rotated/expired CF_ACCESS_CLIENT_ID or SECRET degrades every public reader request to a generic 502 'temporarily unavailable', indistinguishable from the device just being asleep.

**Impact** medium · **Likelihood** low · proposed by `cloudflare-workers-planner`

**Mitigation.** Log the origin response status distinctly (403 from Access vs timeout vs 5xx) even though the client-facing response stays generic, so this shows up in Workers Logs/tail rather than being silently absorbed.

### 42. The operator locks himself out - no email reset, single credential.

**Impact** medium · **Likelihood** low · proposed by `betterauth-planner`

**Mitigation.** This is a deliberate trade for removing an email-provider dependency. The documented recovery is the bootstrap script run against the identity store. Record the credential in the password manager and its NAME (not value) in the AGENTS.md secret index.

### 43. The Cache API is per-datacenter, not globally replicated - a document could appear 'still shared' at a PoP the operator hasn't hit recently, even though the operator revoked it and verified via a different PoP.

**Impact** low · **Likelihood** medium · proposed by `cloudflare-workers-planner`

**Mitigation.** This is inherent to the design and already an accepted trade (60s is the deal). Worth stating explicitly in any user-facing 'unshared' confirmation copy so the operator's mental model matches reality rather than assuming instant global effect.

### 44. Cookie-cache maxAge gets raised for latency reasons without re-deciding the revocation lag it buys.

**Impact** low · **Likelihood** medium · proposed by `betterauth-planner`

**Mitigation.** Record the number and its meaning in lib/auth.ts next to the setting - 'this is also the sign-out lag' - the same way CACHE_MAX_AGE_SECONDS = 60 in the existing Worker is annotated as both freshness and revocation ceiling.
