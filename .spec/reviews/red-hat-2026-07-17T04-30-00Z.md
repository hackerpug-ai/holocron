## HIGH Confidence Findings (Reviewer Agreement: HIGH)

### H1: `generateText` used instead of `generateObject` with `responseFormat: json_schema` — core constrained-decoding requirement not met
- **Severity**: CRITICAL
- **Confidence**: HIGH (both reviewers agree)
- **Location**: `extract-structured.ts:134-148`, `probe-capability.ts:80-98`
- **Evidence**: Both files `await import('ai').generateText(...)` with a manual JSON prompt string. Zero references to `response_format`, `responseFormat`, or `json_schema` in either file.
- **Expected**: Task struct-1 DESIGN NOTES (line 200): `pattern: resolveModel(role) → generateObject({schema, responseFormat: json_schema}) → Zod.parse()`. Task MUST constraint: "MUST Use json_schema constrained decode."
- **Impact**: The "constrained-decode mode" is a fiction. All calls are effectively repair-loop mode (model outputs free text, Zod validates after). The sprint's core value proposition (json_schema constrained decoding on the local fleet) is not delivered.
- **Fix**: Switch to `generateObject({ schema, model: fleetModel })` from `ai` SDK, which sends `response_format: { type: "json_schema" }` on the wire and enables token-level schema enforcement on backends that support it (llama.cpp grammar, vLLM guided decoding via LiteLLM).

### H2: Fleet Role Manifest `structuredOutput` flag never read
- **Severity**: HIGH
- **Confidence**: HIGH (both reviewers agree)
- **Location**: `extract-structured.ts` (entire file — zero `structuredOutput` references)
- **Evidence**: `rg -n 'structuredOutput' services/platform/src/inference/extract-structured.ts` → 0 matches. `rg -n 'structuredOutput' services/platform/src/inference/probe-capability.ts` → 0 matches.
- **Expected**: struct-1 MUST constraint (line 17): "MUST Check the Fleet Role Manifest structuredOutput flag to select constrained vs repair mode."
- **Impact**: The mode-selection logic the probe computes is never consumed by the extraction pipeline. Every role takes the same code path regardless of capability. Acknowledged by sprint-goal-state.json low_notes: "Probe mode (constrained/repair) computed but not yet consumed by extractStructured" — but was classified as LOW, should be HIGH.
- **Fix**: Import the manifest, read `role.structuredOutput`, select the structuring strategy before the repair loop.

### H3: Tripwire is INPUT regex scanning, NOT model OUTPUT guardrail
- **Severity**: HIGH
- **Confidence**: HIGH (both reviewers agree)
- **Location**: `extract-structured.ts:95-118`
- **Evidence**: Tripwire patterns (SSN, credit card, API key, password) are matched against the `input` string BEFORE calling the model (lines 108-118). The BlockedError is thrown before `resolveModel` is even called (line 121 is AFTER the tripwire check).
- **Expected**: struct-1 AC-3: "GIVEN: tripwire fixture WHEN: calling extractStructured() and tripwire fires mid-extraction THEN: throws typed BlockedError." The fixture description: "Processor detects PII in output and trips tripwire." This describes an OUTPUT-side processor (Mastra guardrail), not input pre-filtering.
- **Impact**: A model that GENERATES sensitive content (e.g., reproduces an SSN from a document summary prompt) will pass through undetected. The tripwire only catches text the operator already provided as input — input sanitization, not extraction safety. The secondary catch (lines 204-211, `err.message.includes('tripwire')`) depends on the AI SDK including "tripwire" in error strings, which is fragile and not how Mastra processors work.
- **Fix**: Implement a Mastra processor/guardrail that inspects model output and trips on sensitive content. Or at minimum, scan `result.text` (the model's output) in addition to `input`.

### H4: `holo extract:status` returns `NOT_IMPLEMENTED` — AC-2 requirement unmet
- **Severity**: HIGH
- **Confidence**: HIGH (both reviewers agree)
- **Location**: `holo.ts:1831-1858`
- **Evidence**: Returns `{ ok: false, error: 'NOT_IMPLEMENTED', message: 'extraction status tracking is not yet implemented' }` with exit code 1. Code comment: "This is a placeholder for future implementation."
- **Expected**: struct-1 AC-2: "holo extract:status shows extraction_failed; no row committed." Gate step 5: "holo extract:status <id> — reports extraction_failed with no committed row."
- **Impact**: Key AC unmet. Gate step 5 was "deferred" (see gate pre-check finding G-DEFERRED below) but sprint claims `met:true`. Without status tracking, the "never-silently-accept" invariant is unverifiable through the operator interface.
- **Fix**: Implement extraction state persistence (at minimum an in-memory map keyed by extraction ID) and have `extractStructured` record status on success/failure. `extract:status` reads and reports it.
