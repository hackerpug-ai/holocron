## Exactly-Once Transaction Semantics (audited)

The durable-effect contract is provably exactly-once, not merely at-least-once:

- **UNIQUE keys**: `queue_outbox_key_uidx`, `queue_effects_key_uidx`, `queue_inbox_key_uidx` (`durable-effect.ts:67,77,89`) — physical impossibility of duplicate effect/outbox/inbox rows per key.
- **Atomic effect+dedupe**: `dispatchAndAck` writes the effect AND the inbox dedupe row inside ONE `sql.begin` (`durable-effect.ts:175-215`); a crash at `after-dispatch-before-ack` rolls back BOTH (real Postgres tx rollback, modelled faithfully).
- **before-commit**: `beginEffect` crash throws inside `sql.begin` → outbox never committed → recovery commits fresh → exactly one.
- **after-commit-before-enqueue**: outbox committed, dispatch deliberately not invoked (kill before enqueue) → recovery dispatches → exactly one.
- **after-dispatch-before-ack**: full tx rollback (dispatched/effect/inbox all reverted) → recovery re-dispatches, `ON CONFLICT (key) DO NOTHING` on effect/inbox guarantees idempotent apply → exactly one.
- **Priority/DLQ concurrency**: `FOR UPDATE SKIP LOCKED` in both `priority.ts:118` and `dlq.ts:138` → safe multi-worker leasing; expired-lease reclamation (`priority.ts:91-102`) prevents permanent stuck work.
