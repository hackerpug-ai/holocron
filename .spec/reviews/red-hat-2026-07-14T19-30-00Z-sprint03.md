## HIGH Confidence Findings (Both Agents Agree)

### Finding 1 — CRITICAL: Replay contract tests are pure test theatre (tautology)

- **Severity**: CRITICAL
- **Confidence**: HIGH (both agents agree)
- **Type**: Test theatre / semantic stub
- **Location**: `tests/integration/mcp-replay-contract.test.ts:26-58`

**Evidence**: The "replay contract" test reads a static JSON file and asserts that `first_call_result.subscriptionId === second_call_result.subscriptionId`:
```typescript
const first = fixture.first_call_result.subscriptionId;  // reads "kg_replay_001"
const second = fixture.second_call_result.subscriptionId; // reads "kg_replay_001"
expect(second).toBe(first); // tautology — same file, hand-authored identical values
```

Both values are in the SAME hand-authored JSON file (`add_subscription_replay.json`). No tool is ever invoked. No Convex backend is called. No Mastra server is contacted. No MCP protocol message is sent. The test proves that the fixture author typed `"kg_replay_001"` twice — not that the real `add_subscription` tool has any idempotency mechanism.

**Expected** (per AC-2, mcp-manifest-03): "the replay control test invokes add_subscription twice with the same identifier+sourceType and asserts both calls return the same subscriptionId"

**Fix**: Either (a) invoke the real MCP tool through the Mastra server and verify de-duplication, or (b) at minimum cross-validate the fixture's `idempotency_key` against the manifest's `replay.idempotency_key` field and the real Zod schema's dedup logic. The current implementation proves nothing about real behavior.

### Finding 2 — HIGH: All fixtures are hand-authored synthetic data, not captured from real behavior

- **Severity**: HIGH
- **Confidence**: HIGH (both agents agree)
- **Type**: Semantic stub (fixtures claim provenance they don't have)
- **Location**: `services/platform/tests/fixtures/mcp-manifest/*.json` (all 49 files)

**Evidence**: Every fixture contains fabricated placeholder data:
- `store_document_success.json`: `"documentId": "kg_doc_store_001"` — not a real Convex ID (format would be like `jd7k4q...`)
- `findRecommendations_success.json`: `"name": "Jane Doe"`, `"email": "jane@example.com"`
- `get_research_session_success.json`: `"_id": "kg_rs_001"`, `"topic": "MCP protocol compatibility"`
- `shop_products_success.json`: `"url": "https://amazon.com/dp/B0XXXXX"` — literal placeholder
- `add_subscription_replay.json`: `createdAt: 1720915200000` — hardcoded timestamp reused across files

No fixture contains capture metadata (no trace ID, no request envelope, no capture timestamp, no Convex ID format).

**Expected** (per AC-3, mcp-manifest-03): "MUST capture frozen success/error fixtures from the REAL tool behavior"

**Fix**: Either capture from real tool execution or revise the AC language to acknowledge fixtures are representative examples, not live captures.

### Finding 3 — HIGH: verify-manifest gate validates only 4 of 10+ per-tool fields

- **Severity**: HIGH
- **Confidence**: HIGH (both agents agree)
- **Type**: Half-implementation
- **Location**: `services/platform/src/mcp/verify-manifest.ts:50-82`

**Evidence**: The gate's validation loop checks only:
1. Entry exists in manifest (`not_in_manifest`) — `verify-manifest.ts:52-58`
2. `input_schema != null` (`input_schema_null`) — `verify-manifest.ts:60-66`
3. `transports` non-null and non-empty (`transports_null`) — `verify-manifest.ts:67-73`
4. `{toolId}_success.json` file exists (`fixtures_missing`) — `verify-manifest.ts:74-81`

**NOT checked** (confirmed via `rg` — zero references in verify-manifest.ts):
- `output_schema` — can be null, gate passes
- `defaults` — can be empty `{}`, gate passes
- `errors` — can be `[]`, gate passes
- `pagination` — never validated
- `side_effects` — never validated
- `idempotency` — never validated
- `replay` — never validated, even for mutation tools
- `fixtures` field on the manifest entry itself — all 44 entries have `fixtures: null`
- Error fixture files — gate only checks `_success.json`

A manifest entry with `output_schema: null`, `errors: []`, `replay: null` for a mutation tool passes the gate as long as `input_schema` is non-null and a `_success.json` file exists.

**Expected** (per mcp-manifest-04 AC-1): "MUST require, per tool, a manifest entry with frozen fixtures (success + error)"

**Fix**: Add field validation checks to `buildVerifyReport` for `output_schema`, `errors.length > 0`, and `replay != null` when `side_effects != null`.
