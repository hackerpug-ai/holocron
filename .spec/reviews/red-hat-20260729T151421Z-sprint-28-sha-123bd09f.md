## Executive Summary

QA8 correctly changes the standalone R2 proof to use the effective credential tuple and its live probe still requires List allowed plus sacrificial `drill-neg/<uuid>` Put and API Delete denial. However, the same-parent-ID exception is not fail-closed when the writer secret cannot be resolved, and `verify-restore-creds.sh` drops the restore session token when it is supplied in the canonical secrets file. ## High Findings

### H1 — Same-parent-ID exception accepts an unverified writer-secret relationship

**Confidence:** High (source trace plus deterministic reproduction)

The exception requires a distinct restore secret, but each entry point treats that as true merely because no writer secret is available for comparison. For example, provision rejects equal secrets only when `AMBIENT_R2_SECRET_ACCESS_KEY` is non-empty, then accepts a same-parent Access Key ID with any non-empty session token at [provision-fresh-restore-target.sh:177](../../scripts/provision-fresh-restore-target.sh#L177) and [provision-fresh-restore-target.sh:182](../../scripts/provision-fresh-restore-target.sh#L182). The equivalent conditional logic appears in [prove-r2-readonly.sh:547](../../scripts/prove-r2-readonly.sh#L547), [verify-restore-creds.sh:531](../../scripts/verify-restore-creds.sh#L531), and [run-fire-drill-on-fresh-target.sh:557](../../scripts/run-fire-drill-on-fresh-target.sh#L557).

In an isolated synthetic fixture, `REQUIRE_LIVE_R2_RO=1` provisioned successfully with the same parent Access Key ID, a non-empty session token, and no writer secret available to compare. This proves the documented “distinct secret” condition is not established before the tuple is accepted.

**Required remediation:** for a same-parent-ID exception, resolve both parent Access Key ID and parent secret from the authoritative source and require a non-empty, explicitly unequal restore secret plus a non-empty restore session token. If either parent identity field is unavailable, refuse before provision/fire-drill rather than infer distinctness.

### H2 — Verifier loses `R2_RESTORE_SESSION_TOKEN` from canonical secrets input

**Confidence:** High (source trace plus deterministic reproduction)

[verify-restore-creds.sh:142](../../scripts/verify-restore-creds.sh#L142) imports `R2_RESTORE_ACCESS_KEY_ID` and `R2_RESTORE_SECRET_ACCESS_KEY` from `secrets.yaml`, but its parser omits `R2_RESTORE_SESSION_TOKEN`. Its tuple check then reads an empty token at [verify-restore-creds.sh:530](../../scripts/verify-restore-creds.sh#L530) and rejects the valid Cloudflare shape at [verify-restore-creds.sh:535](../../scripts/verify-restore-creds.sh#L535).

An isolated synthetic `secrets.yaml` containing same parent Access Key ID, distinct secret, and non-empty `R2_RESTORE_SESSION_TOKEN` deterministically produced `FAIL: incomplete Cloudflare temporary credential tuple (same parent Access Key ID without session token)` and exit 1. This breaks the supported temporary-credential restore path when invoked through the verifier's normal secrets-file workflow.

**Required remediation:** import `R2_RESTORE_SESSION_TOKEN` beside the restore ID and secret, preserve the established env-over-file precedence, and add a behavioral test using a secrets-file fixture—not just process environment values.

## Medium Findings

### M1 — Live denial proof is not bound to the credential tuple consumed by provision/fire-drill

**Confidence:** Medium

The standalone proof is sound: it requires successful List at [prove-r2-readonly.sh:373](../../scripts/prove-r2-readonly.sh#L373), denied sacrificial Put at [prove-r2-readonly.sh:389](../../scripts/prove-r2-readonly.sh#L389), and denied `s3api delete-object` at [prove-r2-readonly.sh:441](../../scripts/prove-r2-readonly.sh#L441). But provision only checks credential shape and creates the target; it never invokes that proof, while the runner directly starts the child at [run-fire-drill-on-fresh-target.sh:683](../../scripts/run-fire-drill-on-fresh-target.sh#L683). A separately run proof is therefore not bound to the exact tuple later consumed by the restore.

**Recommendation:** either run the live proof immediately before consuming the tuple or require a non-secret, tamper-evident successful proof attestation bound to a safe fingerprint of the effective tuple. Keep the sacrificial-key restriction intact.

### M2 — QA8 tests leave verifier/fire-drill behavior protected only by source-text assertions

**Confidence:** High

The new tests execute provision and the standalone proof, but the runner and verifier checks are regexes over source text at [sprint28-s28r3-qa8-gate-fix.test.ts:287](../../services/platform/tests/integration/sprint28-s28r3-qa8-gate-fix.test.ts#L287) and [sprint28-s28r3-qa8-gate-fix.test.ts:296](../../services/platform/tests/integration/sprint28-s28r3-qa8-gate-fix.test.ts#L296). They would remain green if the verifier stopped importing the token (the actual H2 defect) or the runner ceased mapping it into its `env -i` child.

**Recommendation:** add mutation-resistant process tests for all four scripts: valid same-ID/distinct-secret/token fixtures, missing token, equal secret, unavailable parent secret, and a recorder child that asserts the session token is present without serializing it.

## Low Finding

### L1 — Mint flow logs a partial Access Key ID

**Confidence:** High

[prove-r2-readonly.sh:243](../../scripts/prove-r2-readonly.sh#L243) prints the first six characters of a minted access-key identifier. No secret or session token is printed, but this conflicts with the task's strict no-credential-value logging intent.

**Recommendation:** log only that minting succeeded; omit the key prefix.
