## Executive Summary

Two independent reviewers were dispatched against the already-"APPROVED" sprint. They converge on four issues strong enough to block: (1) a PII echo in `BlockedError` that turns a data-loss-prevention control into a data-recording vector; (2) the AC-3 "tripwire during extraction" gate step exercises the **input** tripwire (SSN in the prompt) rather than the **mid-extraction output** tripwire the AC specifies, so the headline blocked-on-synthesized-sensitive-data path is unproven; (3) `struct-repair-loop.test.ts` asserts "a valid object was returned" but never that the repair loop actually repaired anything; (4) gate step 5 depends on a gitignored `.tmp/extractions/` file that cannot survive a clean checkout. The sprint's mechanical core is sound — `extractStructured` composes `resolveModel` (never bypasses), calls `generateObject` for constrained decode, re-validates via Zod, bounds repairs at `MAX_REPAIR_ATTEMPTS=3` with an honest for-loop comparison, and throws typed `ExtractionFailedError`/`BlockedError`. Zero stubs, zero `z.any()`, zero `@ts-ignore`, zero cloud calls. The defects are in the safety perimeter and the evidence strength, not the happy path.

## HIGH Confidence Findings (both reviewers agree + lead-verified)

- [ ] **H1 — CRITICAL: Tripwire echoes matched sensitive data into persisted storage + CLI** | Severity: **CRITICAL**
      Location: `services/platform/src/inference/extract-structured.ts:366-367` (input) and `:438-439` (output)
      Agents: `code-reviewer` (primary), lead-verified; `mastra-reviewer` did not flag (gap in domain review)
      Evidence (confirmed by reading source):
      ```ts
      // :366-367
      details: `Detected ${inputTripwire.matches.length} sensitive data pattern(s) in input: ${inputTripwire.matches.slice(0, 3).join(', ')}`,
      patterns: inputTripwire.matches.slice(0, 5),   // raw matched values
      ```
      The `BlockedError` payload — persisted to `.tmp/extractions/<id>.json` (`:198-207`) and echoed to CLI stderr — contains the **literal matched strings** (SSNs, credit-card numbers, API keys, passwords). Gate log `step6-tripwire.log` proves it in the wild: `"details":"...input: 123-45-6789"`, `"patterns":["123-45-6789"]`. The control whose entire purpose is to prevent sensitive data from flowing onward **records that same sensitive data** in a status file and operator output. In the single-user tailnet trust model the blast radius is the operator's own disk/logs, but a DLAT control that leaks the data it caught is a design defect regardless of trust boundary.
      Expected: redact matched values before persisting/echoing (e.g. `"SSN pattern matched (redacted)"`, `patterns: ["SSN", "CREDIT_CARD"]` — pattern *kind*, not value).
      Fix: replace `matches.slice(...)` with a count + pattern-kind label; never serialize the raw capture group.

- [ ] **H2 — The AC-3 "tripwire during extraction" path is unproven** | Severity: **HIGH**
      Location: `extract-structured.ts:428-441` (output tripwire, dead in gate); exercised instead `:361-369` (input tripwire)
      Agents: `mastra-reviewer` (G2), `code-reviewer` (AC-3 PARTIAL) — **independent agreement**
      Evidence: gate step 6 input = `tripwireInput` containing `"My SSN is 123-45-6789..."`; `findTripwireMatches(input)` at `:361` matches **before** `resolveModel` is called (`:372`), so the model is never invoked and the **output-side** tripwire at `:434` (which scans `JSON.stringify(object)` for sensitive data the model *synthesized*) never runs. `struct-tripwire-blocked.test.ts:89-166` does the same. The output tripwire code exists (REDHAT-FIX-H3) but has **zero gate or test coverage**. AC-3 says "tripwire **during** extraction" — the gate proves the *input* tripwire, not the named *mid-extraction* one. A model that hallucinates an SSN from clean input would be caught by the code, but this safety path is unvalidated.
      Expected: a gate step / test with **clean input** that induces the model to emit sensitive output (or a fixture that returns a canned sensitive object), forcing the `:434` path to fire and prove `output_sensitive_data_detected`.

- [ ] **H3 — Repair loop is not behaviorally asserted; a stub would pass** | Severity: **HIGH**
      Location: `tests/integration/service/struct-repair-loop.test.ts:138-174` ("malformed-once enters repair loop")
      Agents: `mastra-reviewer` (G5), `code-reviewer` (FAIL — Test Theatre) — **independent agreement**
      Evidence: the test titled "malformed-once enters repair loop" asserts only `simpleSchema.safeParse(result).success`, `fleetCount >= 1`, `anthropicCount === 0`. It **never** asserts `attempts > 1`, never reads loop state, never verifies a repair actually occurred. The `malformedOnceInput` fixture is **prompt-based** (a text asking the model to return bad JSON once then good) — non-deterministic; if the model returns valid JSON on attempt 1, the repair loop is never entered and the test still passes. A stub `extractStructured` returning the hardcoded `goodOutput` would pass this test. The cap *is* honestly exercised by `struct-explicit-fail` (always-malformed → 3 real `AI_NoObjectGeneratedError`), but the **repair-success** half of AC-1 is unproven.
      Expected: instrument the loop (expose `attempts` via the status record / a test hook) and assert `attempts === 2` for the malformed-once case; or drive a deterministic malformed-then-valid fleet fixture (not a prompt).

- [ ] **H4 — Gate step 5 is non-reproducible from a clean checkout** | Severity: **HIGH**
      Location: `.gate-evidence/.../step5-extract-status.log` depends on `.tmp/extractions/222ac4d3-…-e2d1a4256fa3.json`
      Agents: `code-reviewer` (primary); `mastra-reviewer` (G3 — related: file store not DB)
      Evidence: `getExtractionStatus()` (`extract-structured.ts:152-159`) reads from `EXTRACTIONS_DIR = .tmp/extractions/` (`:128`), which is gitignored. The hardcoded id in gate step 5 only resolves because a **prior** extraction in the same run wrote that file. A reviewer checking out `f4e07af` clean cannot reproduce step 5 — the status file does not exist. The "Database query returns 0" oracle in AC-2 is also not literally true: there is no extractions DB table; `committed:false` is a JSON boolean, not a SQL result.
      Expected: gate step 5 must run `holo extract --fixture always-malformed` and pipe its emitted `<id>` into `holo extract:status <id>` in a single shell sequence, so the step is self-contained.

- [ ] **M4 — Task AC-2 oracle over-promises a database that doesn't exist** | `mastra-reviewer` (G3) / `code-reviewer`

The never-commit invariant is **honestly enforced in code** (no write path commits on failure), but the observable contract ("Database query returns 0") cannot be satisfied as written.

- [ ] **M5 — Gate logs step4 & step6 carry manual `EXIT_CODE=1` annotations of unknown provenance** | `code-reviewer`
      Lines like `EXIT_CODE=1` appear after the JSON in `step4-always-malformed.log` and `step6-tripwire.log`. These are not CLI-emitted; they're wrapper annotations. Real output is confirmed (the JSON is genuine), but undocumented annotations reduce evidence trust. Document the capture wrapper or strip the annotations.
